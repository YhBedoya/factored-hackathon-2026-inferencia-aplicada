### T9 — Eval harness starts the backend on Windows (SelectorEventLoop)
Changed: `eval/harness/runner.py` only (`_start_backend`): on `sys.platform == "win32"`, appends `--loop asyncio:SelectorEventLoop` to the uvicorn command. No new module, no `sys.path`/`PYTHONPATH` change, no `backend/app` edit.
Why this shape: uvicorn 0.37's `--loop` accepts a `module:attribute` import string that must resolve directly to a zero-arg `Callable[[], AbstractEventLoop]` (`Config.get_loop_factory`, `uvicorn/config.py:555`) — unlike the 4 built-in names, it is *not* called with `use_subprocess=...` first. `asyncio.SelectorEventLoop` (the class) already satisfies that signature, so no `eval/harness` helper module was needed (an earlier attempt at a `win_loop.py` with a `use_subprocess`-taking factory failed with `TypeError: ... close() missing 1 required positional argument: 'self'`, since uvicorn treated the returned function itself as an already-instantiated-or-not loop, not a factory-of-factories — removed).
Facts the next tasks/Dev A need: **confirmed by live proof** — with `--loop asyncio:SelectorEventLoop`, the backend subprocess reaches `Application startup complete`, `db: up` on `/api/v1/health` every time (psycopg async + the LangGraph checkpointer pool connect fine; no `ProactorEventLoop`/`PoolTimeout` anywhere in the log). **Separate, pre-existing issue surfaced by this fix (not fixed here, flagged per the task's own instruction not to work around it):** `/api/v1/health` never returns `200` on this host — `redis: down` on every single call. Root cause isolated by hand: `app/core/redis.py`'s `ping_redis()` wraps `Redis.ping()` in `asyncio.timeout(2.0)`; on this Windows host, `getaddrinfo("localhost", ...)` (used by `redis.asyncio` to connect) consistently takes ~2.02–2.05s — just over the 2.0s budget — so every ping is cancelled mid-connect and the connection never gets to be reused, repeating forever. Using `redis://127.0.0.1:...` instead of `localhost` in `REDIS_URL` makes every ping instant (0ms) and `db`+`redis` both report `up`. This reproduces identically under plain `asyncio.Runner(loop_factory=asyncio.SelectorEventLoop)` with no uvicorn/subprocess involved, and is unrelated to Proactor vs Selector (the DNS-resolution executor path is identical for both) — it only became visible now because the app no longer dies earlier at the checkpointer pool. Not touched: the task's acceptance forbids any `backend/app` change, and explicitly says a different-reason failure (Redis reachable but slow to resolve from this host) should be reported, not worked around. Dev A/human call: bump `_PING_TIMEOUT_SECONDS`, or have local `.env`/`REDIS_URL` defaults use `127.0.0.1` instead of `localhost` for this host class.
Also found and cleaned up (not fixed, out of scope): `_stop_backend`'s `proc.terminate()` only signals the immediate `uv run` child on Windows; the actual `uvicorn.exe`/`python.exe` descendants it spawns are left running (confirmed via `tasklist` after normal script exits) — every manual proof in this task leaked processes and clone DBs until killed/dropped by hand. Windows-only, unrelated to the event-loop fix itself.
