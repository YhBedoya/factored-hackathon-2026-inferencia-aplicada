## Decisions settled by the human

1. **Old test `test_agent_plan_check.py::test_precondition_rejects_blocked_card`: update it (settled).** Its last assertion, `pytest.raises(PolicyDenied)` around `issue_plan([PlanStep(tool="cards.unlock_card", ...)], None)`, protects the executor's agent-path gate: with `intent=None`, a write tool whose `tools.yaml` entry has no `preconditions` block gets `rule_hit tool_not_allowed` and `PolicyDenied`, and no token. That behaviour still exists after S2. `disputes.create_claim` still has no `preconditions` block, and nothing else covers the `intent=None` gate: `test_r2_confirmed_writes.py` covers `tool_not_allowed` only for a tool outside an intent's `allowed_intents`. Only the example tool is stale, because D5 gives `cards.unlock_card` a `preconditions` block. T2 changes that one assertion's step to `PlanStep(tool="disputes.create_claim", args={"tx_ids": ["TRX-1"], "answers": [], "priority_flags": []})` and keeps `PolicyDenied`. The solution does not change to keep the test. **Spec success criterion 1 is amended:** the diff may touch this one assertion in this one existing test file.
2. **Forced files outside the spec's touch map: accepted, built in T9 (settled).**
   - `backend/app/domains/conversation/runner.py`: `start_turn` and `_run_turn` accept `resume: "step_up_cancel"`, and the new nodes get `path: "agent"` (D18), labels and a real route.
   - The `resume` Literals in `graph.py`: `TurnInput`, `GraphState`, `run_turn`.
   - `docs/diagrams/turn-graph-v0.mmd`, regenerated by `make graph-diagram`, because `test_graph.py::test_graph_compiles_and_diagram_is_current` compares the two.
3. **Done when 1 (the browser run) cannot run from this worktree.** Every `latam-cs-*` container bind-mounts the **main checkout**: `backend/app`, `policies/` and `frontend/`, not this worktree. The ES/PT browser run in success criterion 5 therefore needs the branch checked out in the main checkout (or merged), `AGENT_ENABLED=true`, a 6-digit `DEMO_OTP_CODE` in that `.env`, and `make up`. No task does that. It is the verifier's or the human's step (Verification map, row 5).

Readings the spec left open. **The human accepted all seven as written; they are settled.**
- **Rejection string.** `rejected (<handle>: <code|ok>, ...)` lists every step in order, by the handle Cardy passed. It replaces S1's `step n:` form. S1's tests only check `startswith("rejected")` and `count("unknown_reference")`.
- **Post-OTP turn tools.** On the turn after the OTP, where the plan was just issued, Cardy's tools drop `propose_plan` and `pass_to_flow`, the way S1 drops `pass_to_flow` on a click turn. This keeps the card she is describing as the one on screen.
- **Any non-cancel turn at the agent OTP pause** (typed text that got past the API gate, a stale button, a pick) goes to `agent_step_up`. That node changes nothing and sends the OTP UI again (D15, second half). Only text goes to `agent_address` at the address pause. Other inputs there fall through, as S1 D27's stale click.
- **Segments.** A plan's segments are one per distinct intent of its steps, in step order: lock and block → `card_block` (route `card_block`), unlock → `card_unlock` (route `card_unlock`), replace → `replacement_request` (route `replacement`). In the D2 case the `card_unlock` segment is `abstained`, also when AQ4 suppresses the offer.
- **The confirm card for a new-address replace step** shows the card mask only. The masked address `•••, <city>` is shown for `on_file` only (D9).
- **The generated client (`frontend/src/client/types.gen.ts`) is not regenerated.** Its `resume?: 'step_up' | null` goes stale, which is harmless: `api.ts` posts `{resume: ...}` through the untyped `client.post<…, unknown>`, as `postResume` does. `make client` would also read the main checkout's backend.
- **When the LLM is down,** `agent_step_up` writes its code text itself and clears `escalation_reason`, so the turn ends in `finish` and not in `fallback` (D18).
