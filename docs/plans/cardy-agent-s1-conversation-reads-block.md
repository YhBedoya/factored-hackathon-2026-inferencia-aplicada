# Plan: REQ-cardy-agent-s1 — agent foundation, conversation, reads, lock and block

Spec: [`docs/specs/cardy-agent-s1-conversation-reads-block.md`](../specs/cardy-agent-s1-conversation-reads-block.md) · Branch: `feat/cardy-agent-s1-conversation-reads-block` (off `origin/develop`, 010b43f)

Tasks tagged **[item 5]** are the lock/block plan work (spec D8–D17, tests 1–4, 9, 10 and the token half of test 5). They are the card's "If behind" cut: dropping every [item 5] task leaves a working agent that passes lock and block to the flow, and no earlier task has to be redone.

## Open items for the human

None of these is decided by this plan. Each names the task it touches and what that task does until an answer is in the state file.

1. **D17 threshold (blocks T18 only).** Spec D17 (b) says "two typed turns in a row that end with the same agent plan still open" and cites S0 D4, where the first non-answer replays and the **second** hands off. Test 3 says "a **third** typed turn on the same plan hands off", and its own sequence resets the count on the second typed turn (the plan is replaced). The same question applies to D17 (a).
   - (a) *Recommended:* S0's rule. The first typed turn on a plan shows the card again, the second typed turn on the same plan hands off. Test 3 then needs four typed turns ("sí", the change, then two on the new plan). For (a): asked, asked again, and the third `asked` turn for the same request type hands off (two failures, as `02` §5).
   - (b) Two replays, the third typed turn on the same plan hands off. Test 3 needs five typed turns.
   - (c) The replacing turn counts as the first typed turn on the new plan, so test 3 works as literally written (three typed turns). This contradicts "a replaced plan resets the count".
   T18 stops and reports if the state file has no answer.
2. **Staff-facing text for `agent_round_cap` (T2, T13).** The spec gives the customer text (`handoff_transfer`) but not the staff text. Without it staff read the `human_request` fallback summary and a raw i18n key. Proposed, used unless the state file carries other wording:
   - `handoff_summary._FALLBACK`: ES "El asistente no logró completar la solicitud tras varios intentos." · PT "O assistente não conseguiu concluir a solicitação após várias tentativas."
   - `staff.reason.agent_round_cap`: ES "Límite de pasos del asistente" · PT "Limite de passos do assistente".
3. **Flag turned off while an agent pause is checkpointed.** `graph._entry` does `_FLOW_NODES[pending["flow"]]`; with `flow: "agent"` and the flag off a button or pick turn raises `KeyError`. The spec does not cover it.
   - (a) *Recommended:* with the flag off, a `flow: "agent"` pause is treated as no pause (button or pick → `smalltalk` as a stale click; typed → `understand`, whose `enqueue` cancels the plan).
   - (b) Leave it; the flag is only flipped after `make demo-reset`.
   T15 builds (b) (nothing beyond the spec) unless the state file says (a).
4. **Files outside the spec's touch map that the build forces.** `backend/app/domains/handoff/schemas.py` (`HandoffReason`), `backend/app/domains/conversation/nodes/handoff_summary.py` (item 2), `frontend/src/lib/sse.ts` (the hand-written `ConfirmPayload` type), `backend/app/domains/conversation/sandbox.py` (one `ConfirmedWriteTools(` call), `backend/tests/conftest.py` (`ScriptedLLM`, which the spec's test list requires but success criterion 1 does not list), `docs/diagrams/turn-graph-v0.mmd` (generated by `make graph-diagram`).
5. **The four dev scenarios join every later `make eval SUITE=dev` run**, flag on or off. With the flag off, the multi-card block case will not resolve in one plan. The scenario schema has no field for "needs the flag", and `eval/harness/` is ask-first.


**Replacement amendment (D28–D40, tasks T22–T31).** Not decided by this plan. Each names the task it touches and what that task does until an answer is in the state file.

A. **What the page shows on `409 selection_required` (T31).** The spec adds `selection_required` to `KNOWN_ERROR_CODES`, which renders `errors.<code>`, but gives no text. It also does not say whether the customer bubble that `handleSend` adds before posting stays. (a) *Recommended:* ES "Elige las tarjetas que quieres reemplazar o toca «No, gracias»." · PT "Escolha os cartões que quer substituir ou toque em «Não, obrigado»."; the typed bubble is removed. (b) The same text; the bubble stays. (c) No line is shown (the code is handled before the banner), and the bubble is removed. T31 stops if there is no answer.
B. **`frontend/src/lib/api.ts` is outside the spec's touch map (T31).** The picker submit and the reload decline need a `postCardSelection`. `postSelection` lives in `api.ts`, and `withAuthRetry` is module-private there. (a) *Recommended:* add `postCardSelection(conversationId, cardIds)` to `api.ts`, mirroring `postSelection`. (b) Call the generated SDK from `ChatView.tsx`, which means exporting `withAuthRetry`, so `api.ts` changes anyway. T31 stops if there is no answer.
C. **Reply to a `card_selection` that fails the flow's second gate (T27).** The ids are not a subset of `replacement_card_ids`, which can only happen if the API gate was bypassed. The spec says "the turn changes nothing and the pause stays" and gives no text. (a) Replay the stored open question (the offer text and the picker), as the typed turn at this pause does. (b) Write no segment, so `finish` sends the R11 `fallback` text, with the pause kept. T27 builds (a) unless the state file says (b).
D. **`ToolUnavailable` inside Cardy's call on the Acepto turn (T28).** Today `agent()` returns `escalation_reason: "tool_failure"`, which leads to the fallback handoff even though the blocks were verified. The offer is then lost. D30 covers only an `LLMError` ("Cardy's call fails"). (a) Leave it: handoff and no offer. (b) Treat it like an `LLMError` on a click turn: `agent_code_text`, then the offer. T28 builds (a) unless the state file says (b).
E. **Stale `replacement_card_ids` (T27, T28). This is a reading, so overrule it through the state file.** A pause can end outside `flows/replacement.py`, for example with a `clarification_exhausted` handoff from `_keep_open_question` or a human takeover. The list would then survive, and a later one-card pipeline replacement in the same conversation would read it through the `replacement_card_ids or [selected_card_id]` fallback. The plan has the one-card entries write `replacement_card_ids: None`: the `address_confirm` pause from `_check_active_and_eligibility` (T27) and the D28 one-card agent offer (T28). No one-card text or call changes.
F. **`backend/app/domains/conversation/hosting.py` is outside the spec's touch map (T23).** The checkpointer's msgpack serde allowlist is strict. `CHECKPOINT_TYPES` is derived from fixed roots (`UIEvent`, `ActionResult`, `ConfirmationDecision`, `Fact`, `HandoffEvidence`, `NLUResult`, `TxSelection`), and `test_checkpoint_serde.py::test_serde_allowlist_is_strict_and_complete` asserts that every model in `GraphState` is allowed. A `card_selection: CardSelection` channel therefore fails that test, and in production a checkpointed `CardSelection` would come back as a raw dict. (a) *Recommended:* add `CardSelection` to the roots in `hosting._checkpoint_types`, a one-line change. (b) Leave `hosting.py` alone. The channel then cannot hold the model, which contradicts the spec's `card_selection: NotRequired[CardSelection | None]`, so the spec would change. T23 stops before `hosting.py` if there is no answer.

Readings this plan relies on (the spec leaves them to the plan or is silent; overrule any of them through the state file):
- **Final output of `tool_loop`** (spec: "how the final output is obtained is the plan's"): `schema` is bound as one more tool beside the `LoopTool`s, with automatic tool choice. See Components.
- **Per-turn `GraphState` channels, not `TurnState` fields** (S0 precedent `asked_ui`, `non_answer_counted`): `agent_enabled`, `agent_labels`, `agent_code_text`, all reset by `load_session`.
- **A read tool that raises `ToolUnavailable`** ends the turn as today's tool failure: `escalation_reason: "tool_failure"` → `fallback → handoff_summary → handoff` (`02` §5, 06 R11). `AccessDenied` reaches `_guard_access` unchanged.
- **D5 turn** records `path: "agent"` and `degraded: false` (code on the agent path wrote the reply; the pipeline did not run).
- **`outcome: "redirected"` needs a `scope_facts` call in the same turn**, because `nlu_result.status` comes from that topic's `kind`. Without one the output is invalid.
- **Everything that is not conversation, a redirect, one of the five reads, or lock/block passes** (`pending_reversal_explain` and the stretch intents included), per the spec's Objective.

**1. Tool loop (`core/llm`).** `tool_loop` binds the `LoopTool`s and `schema` (as an output tool) with `bind_tools`, automatic tool choice. Each provider call is one attempt: `find_pii` over `system`, every message and every tool result first; one `trace_llm_call` and one `_finish` ledger row. A response whose only tool call is the output tool ends the loop: `schema.model_validate`, then `validate`. A response with no tool call, a schema failure or a `validate` reason is invalid output: one retry with the reason, then `LLMInvalidOutput`. A response with other tool calls is a round: handlers run in order, results are appended. After `max_rounds` rounds the model gets one more call; if it is not the output, `LLMRoundCap`. A handler's exception leaves `tool_loop` unchanged. Depends on nothing in `domains`.

**2. Agent package `backend/app/domains/conversation/agent/` (new).** `schema.py`, `refs.py`, `checks.py` (code only); `reads.py` (read tools and `scope_facts` over `config["configurable"]["bank_tools"]` and `get_policies().scope`); `node.py` (the only module that calls `llm.tool_loop`); `plan.py` and `confirm.py` ([item 5], no `app.core.llm` import). Depends on component 1, `nodes/compose.py`, the flows' fact builders and the policy bundle.

**3. Graph and runner wiring.** `load_session` writes `agent_enabled`. With it true, `_entry` keeps human mode, `llm_unavailable`, a legal-keyword hit and any pipeline flow-question `pending` on today's path, sends a pick on an agent list to `agent`, a button on an agent plan to `agent_plan`, and everything else to `agent` through `summarize` (its edge to `understand` becomes conditional). `agent` ends in `finish`, `understand` (pass or D4), `fallback` (tool failure) or `handoff_summary` (D3, D17). The runner records `nlu_result` with `source: "agent"` from `agent_labels` and `reply_sent.path`.
